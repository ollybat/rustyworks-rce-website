The data behind this site

Everything Spinback publishes is plain JSON over ordinary HTTPS. There is no key to ask for, no sign-up, and nothing you can change: the bot's own status and the files this site reads are the whole of it. Anything the bot has not measured is null or absent, never guessed, and the machine-readable index of all of it is one file: /data/api.json.

What the bot publishes

EndpointStateWhat it carries
/api/status live The bot's own health: online, version string, uptime seconds, guild count, gateway latency, and the kind of storage its settings live in.
/api/shim live Whether the website-check shim is loaded in the bot process, the window it gives the full check, and the cheaper file it prefers.
/api/guilds live The Discord servers the bot is in, as ids and names only.
/api/servers not live yet The Rust servers the bot looks after, per server, with state and population. The route is written and reviewed and is not published yet, so the Servers page reads /api/status instead and says which source it used.

Every one of these lives on the bot's own host, not on this site. They are labelled live only where a request to them right now answers, and the site itself tells you which source a page read: the Servers page prints it under the filter row.

What this site serves

PathStateWhat it carries
/data/commands.json live Every command, all 35 subcommands and the 12 goals the bot registers, with who may run each one and what it needs set up first. This is the same file the Commands page draws and the site search indexes, so they cannot drift apart.
/data/items.json live The item catalogue Kit Studio uses: display name, short name, stack size, and a note on where each entry came from.
/data/skins.json live The Rust Console Edition store as it was read on 11 November 2026: the store products, the skins inside each one, the release date each product carries, gallery images, and the counts. The file states its own source and date.
/data/api.json live This index, in machine-readable form: the same list, the fields each file carries, and the rules above.
/health.json live The cheapest true answer to "is this site up". A tiny static file, which is why the bot's website check prefers it over the full config check.
/sitemap.xml and /manifest.webmanifest live Every public page, and the install metadata the browser uses to pin the site.

How to read it

// Any language, any language's HTTP client. No headers required.
// The bot's host, for its own endpoints:
//   https://rustyworks-rce-website-production.up.railway.app
//
//   GET /api/status        -> { online, version, uptimeSeconds, guilds, latencyMs, storage, ... }
//   GET /api/guilds        -> { guilds: [ { id, name } ] }
//   GET /api/shim          -> { active, window, raceMs, prefers, follows }
//   GET /api/servers       -> not published yet (405)
//
// And on this site:
//   GET /data/commands.json
//   GET /data/items.json
//   GET /data/skins.json
//   GET /health.json
//
// Cache politely: the site's JSON files carry cache headers, and the bot's
// status answers from memory. One request a minute is plenty for a status
// page; there is no rate limit to test, only a host to be kind to.

What is deliberately not here

  • RCON passwords. No endpoint returns one to anything running in a browser. A page may be told only whether a password is set.
  • The shared settings token and the owner's Discord secrets. There is no endpoint for either, and no way to ask for one.
  • Message content. The bot asks Discord for a single gateway intent, Guilds, so it cannot read ordinary messages and has none to publish.
  • Anything writable. There is no POST, no PUT, no webhook. If a future version adds an action, it will be a Discord command first, not an endpoint here.

Written against the code

This page and its index are kept in step with what actually answers: the bot's endpoints were requested today, and the store data carries the date it was read. When /api/servers goes live, the word not live yet comes off this page in the same push.
